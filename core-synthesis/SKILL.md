# 综合

方法只是中间过程。用户要的是一个能执行的方案，而不是几份各自独立的框架分析。

## 输入与输出

- 输入：`01_issue-tree.md`、`02_method-plan.md`、统一证据账 `03_evidence/`（研究、尽调的结论也在里面）、`04_analysis/`、`05_review-log.md`（有的话）。
- 输出：`06_synthesis.md`。core-storyline 与输出层（out-report、out-chart、out-poster）从这里取内容，不再补新事实。
- 引用：主张写 `[cl-0003]`，直接引原文写 `[M004 p12]`（来源 ID + 定位）。

## 先过两道检查

1. **核实关口**：按 `../core-evidence/SKILL.md` 第 6 节逐条检查“影响结论”的事实。未核实的关键事实 → 结论改写成“如果……则……”，并列入“需要先确认的问题”。
2. **审查问题清零**：`05_review-log.md` 里“阻塞”和“重要”级别的问题，要么已修复，要么写明不改的理由。

## 综合四件事

1. **理清关系**：结论之间有没有冲突（一个要求聚焦，另一个要求扩张）？有没有依赖？有冲突就取舍，并说明理由。
2. **排出先后**：按依赖关系和影响大小排序。说了可以并行的动作放在同一时段，说了有依赖的排在前后。
3. **对照资源**：人手、时间、预算够不够？不够就砍掉或推后优先级低的动作。
4. **检验能否落地**：每个动作都有负责人、时间、衡量标准。再做一次事前验尸：“如果三个月后这个方案失败了，最可能是因为什么？”把答案变成预防措施。

另加一条：**和“什么都不做”比**。写一句：如果维持现状，会发生什么？方案比维持现状好在哪里？说不出来，方案就还没想透。

只有一个子问题时，综合就是把分析结论转成行动，并做第 3、4 项。

## 强词检查

正文里出现“必然、一定、所有、唯一、彻底、显著”等词时，逐个问：有证据支撑到这个强度吗？没有就改弱或删掉。相关不写成因果，个例不写成普遍，“可能”不写成“必然”。

## 输出格式

默认汇报格式。不设页数和条数上限：第一句是答案，完整论证进正文，过程细节进附录；各节按重要性排序，读者读完前几条就能抓住要点。

```
## 假设（不成立时结论会怎样变）

## 需要先确认的问题
最可能改变结论的问题，按影响大小排序，并说明答案不同时结论怎样变。

## 结论（只写一句话，先说答案）

## 背景（SCQA）
- 情境 S / 冲突 C / 问题 Q / 答案 A

## 问题拆解
主导问题 + 子问题及关系（只有一个子问题时省略）

## 各子问题的结论（完整论证：结论、依据、限制；关键数字带主张编号 [cl-xxxx]）

## 综合方案：行动路线图
| 顺序 | 动作 | 负责人 | 时间 | 衡量标准 |

## 风险与预防（事前验尸）

## 附录 A：各子问题的分析过程
## 附录 B：分析方法说明（每个子问题用了什么方法、为什么；为什么没用相邻方法；回退记录；经验建议）
## 附录 C：证据账摘录（只列影响结论的主张，完整账在 03_evidence/）
## 附录 D：审查记录（经过哪几种审查、改了什么；未经独立审查时写明）
```

不同领域的正文形态，按方法库的“输出形态”一节调整：

- 企业方向（lib-consulting）：上面的汇报格式。
- 内部管理（lib-management）：结论后直接给能用的表（目标表、分工表、对策表、复盘记录）。
- 个人（lib-personal）：不用 SCQA；按“一次只改一件事”排出先后，第一步今天就能开始。

用户只是自己想把问题想清楚时，可以省去 SCQA 包装，直接给问题拆解、分析表和行动。

## 底线

- 结论先行，一句话，不用分号串好几层意思。
- 以上统下：上层观点是下层的概括；同组观点同类、同一抽象层次。
- 不把“其他”放在最高层级。
- 方法说明要诚实：某个框架对这个问题帮助不大，就直说。
