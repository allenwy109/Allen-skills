# 选方法

选方法最常见的错，是看用户的问法像哪一行就选哪个，然后在没有数据的情况下用推断把方法填满：形式对了，结论是虚的。这个 skill 在“选”和“做”之间加一道关口。

## 输入与输出

- 输入：`01_issue-tree.md`（主导问题、子问题、关键事实清单）。没有任务文件夹时，用回答里的问题拆解。
- 输出：`02_method-plan.md`（模板见 `assets/method-plan-template.md`）；没有任务文件夹时写进回答的附录“分析方法说明”。

涉及需求、竞争、定价的 L2/L3 决策研究，先读 `../core-evidence/references/decision-research-contracts.md` 的方法覆盖问题。它们用于确认是否考虑过相关视角，不要求、也不允许机械套用全部框架。

## 选方法关口：每个子问题走五步

### 1. 写画像

用四个字段描述子问题，不看措辞看性质：

| 字段 | 选项 |
|---|---|
| 要做什么 | 界定问题 / 找原因 / 评估选项 / 规划执行 / 表达结论 |
| 时间方向 | 已经发生的 / 将来的 |
| 手上的信息 | 有数据 / 只有定性描述 / 几乎没有 |
| 要交付什么 | 一个判断 / 一个排序 / 一个数字 / 一个方案或表格 |

### 2. 查选法表

按子问题的领域读对应方法库的 SKILL.md：

- 企业方向：`../lib-consulting/SKILL.md`
- 内部管理：`../lib-management/SKILL.md`
- 个人：`../lib-personal/SKILL.md`

选法表有四列：情况、首选、**前提**（缺了就不能用）、**换用**（如果……→ 改用……）。按画像找到行，不按关键词找。

### 3. 查前提

逐条核对“前提”列。前提不满足时只有两条路：

1. **先补信息**：前提缺的是公开信息，交给 core-evidence 去查；缺的是只有用户知道的信息，写进“需要先确认的问题”。
2. **换要求更低的方法**：按“换用”列降级，例如拿不到份额数据 → BCG 改为定性 KSF 对比；没有客户访谈 → 客户旅程改为基于已知投诉和丢单记录的卡点清单，并标明局限。

**不允许用推断把需要数据的方法填满。** 实在要做示意，必须在标题写“示意，数据为假设”，结论不能依赖它。

### 4. 预演产出

用一句话写出：这个方法做完，会产出什么？例如“一张按利润贡献排序的产品表，指出哪两条产品线拖累了毛利”。然后问：**这句话能直接回答子问题吗？** 不能，就换方法或改子问题。方法计划必须回填实际产出；只列“3C”“五力”等方法名而没有执行产出，不算使用过该方法。

### 5. 说清为什么不用相邻方法

在做之前写一句：“不用 X，因为……”。这一句写不出来，说明还没想清楚两个方法的区别，回到第 2 步。

## 组合规则

- 每个子问题至少一个方法；每个方法都必须对应一个子问题。
- 每个子问题默认只用一个方法，够用就停。第二个方法只在它回答同一子问题的**另一个侧面**时才加（鱼骨图铺开原因，5WHY 深挖主因），并写明多带来了什么。
- 子问题属于其他领域时，直接用那个方法库的方法，不要勉强用本领域的。
- 方法覆盖不到的建议，标“经验建议”，并写需要什么信息来确认。

## 几个方法都像时，按顺序取舍

1. 能用公式拆的优先（天然 MECE，最不容易漏）。
2. 信息少时，优先定性、轻量的方法。
3. 产出离“要交付什么”最近的优先。
4. 仍分不出来，选用户更熟悉的。

## 读卡片，然后做

选定后，**先读方法卡片再动手**。卡片路径在各方法库的 `../lib-*/references/method-index.md` 里。卡片的“前提与不能推出什么”“常见误用”两节要逐条对照。

## 回退规则

分析过程中发现方法的产出回答不了子问题，或前提其实不成立：停下，回到第 1 步重选，并在方法计划里记一笔“原选 X → 改为 Y，因为……”。这些记录是以后修订选法表的素材。

## 不确定时

方法选择本身有争议（两个方法都说得通、结论会因方法不同而不同）时，在 L3 深度下交给 core-review 的“方法审查员”复核。
