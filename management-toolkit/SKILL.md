# 企业内部管理工具箱

这套 skill 解决的是“**定好的事怎么做成、团队怎么带好**”。和咨询分析不同，内部管理的产出不是一份论证报告，而是一张能马上用的表：目标表、分工表、根因分析表、复盘记录、会议议程。所以选方法时要特别看两件事：**团队现在的成熟度**和**这件事是探索型还是重复型**。

## 和 consulting-analysis 的分工

- consulting-analysis 回答“企业该往哪走、为什么经营成这样”。
- 本 skill 回答“方向定了以后，怎么定目标、怎么执行、出了问题怎么查、事后怎么复盘、人怎么带”。
- personal-effectiveness 回答“我自己怎么更高效”：个人的时间、习惯、学习、决策和职业发展。
- 需要把分析结果写成给上级看的汇报时，汇报结构（SCQA、金字塔原理）可以借用 consulting-analysis 的第四步。

## 工作流程

### 第一步：判断管理场景

先弄清三件事，再选方法：
1. **处在哪个环节**：定目标、做计划、执行改进、出了问题、事后复盘、带人、推动变革、开会讨论。
2. **工作性质**：探索型（从 0 到 1，结果不确定）还是重复型（从 1 到 N，有标准）。这决定了很多方法的取舍，比如 OKR 还是 KPI、PDCA 还是敏捷迭代。
3. **规模和正式程度**：个人、一个小组，还是跨部门、全公司。越正式、越跨部门，越需要结构化的方法（8D、方针管理）；越小越日常，越用轻量的方法（5WHY、非正式 AAR）。

信息不够就问用户一两个关键问题。如果要先给出初步方案，就在回答**开头**写明你做了哪些假设，并说明假设不成立时方案会怎样变化，而不是放在结尾顺带一提。

### 第二步：选方法

每次只选 **1 个主方法 + 最多 1 个辅助方法**，并说明为什么用它、为什么不用相邻的那个。

**A. 目标设定与分解**
| 场景 | 首选 | 何时换用 |
|---|---|---|
| 检查单个目标写得好不好 | SMART | 所有目标都适用，是最基础的检查 |
| 探索型、创新型工作，或自驱型团队 | OKR | 不宜直接挂钩考核，否则大家只敢定保守目标 |
| 标准化、重复性工作的日常监控 | KPI | 需要鼓励突破时，KPI 上面再加 OKR |
| 公司战略要落成各层面的指标 | 平衡计分卡 + 战略地图 | 适合成熟企业、战略目标多维度的情况 |
| 多年战略要逐层分解到部门和个人 | 方针管理（Hoshin Kanri）/ OGSM | 战略周期长、不希望季度频繁调整时用；变化快的环境用 OKR |
| 大目标分解到具体事项 | 目标多叉树 | 分解后每个子目标都要再过一遍 SMART |

**B. 计划与分工**
| 场景 | 首选 | 何时换用 |
|---|---|---|
| 布置一项任务，怕漏掉要素 | 5W2H | 更复杂的项目用 6W3H 或 WBS |
| 项目要拆成可执行的工作包 | WBS（工作分解结构） | 拆到能指派给一个人、能估算工期为止 |
| 多人协作，职责不清、互相推诿 | RACI（执行、负责、咨询、知会） | 每件事只能有一个“负责”人 |

**C. 执行与持续改进**
| 场景 | 首选 | 何时换用 |
|---|---|---|
| 有标准、可重复的工作，要越做越好 | PDCA | 做完一轮要把有效做法标准化，再进入下一轮 |
| 流程慢、浪费多 | 精益（识别八大浪费、价值流图） | 先用 SIPOC 画出流程边界 |
| 质量波动大，需要用数据说话 | 六西格玛 DMAIC（定义、测量、分析、改进、控制） | 问题简单时用 PDCA 即可，DMAIC 太重 |
| 现场脏乱、找东西费时间 | 5S / 6S | 属于基础管理，不能指望靠它解决深层问题 |
| 不确定性高、需求常变的项目 | 敏捷迭代（小步快跑、定期回顾） | 需求稳定、交付明确时用传统计划即可 |

**D. 出了问题，找原因**
| 场景 | 首选 | 何时换用 |
|---|---|---|
| 同时冒出很多问题，先解决哪个 | 优选矩阵（重要、紧急、变化程度打分）/ 帕累托图 | 有数据时优先用帕累托图找出 20% 的关键问题 |
| 现象清楚，原因单一 | 5WHY | 原因多时先用鱼骨图 |
| 原因多、涉及多个环节或部门 | 鱼骨图（制造业用 5M1E：人、机、料、法、环、测） | 画完要用数据验证，再对主要原因用 5WHY 深挖 |
| 质量或客诉问题，要先止损再根治、防止复发 | 8D | 小问题用 PDCA，8D 流程太重 |
| 战略层面的问题（如份额下滑） | 不在本 skill 范围 | 改用 consulting-analysis 的议题树或 3C |

**E. 复盘**
| 场景 | 首选 | 何时换用 |
|---|---|---|
| 项目或阶段结束，正式复盘 | 复盘四步法 GRAI（回顾目标、评估结果、分析原因、总结规律） | 要先检查目标本身是否定错了 |
| 会议或日常活动后快速总结 | 非正式 AAR（5 分钟：预期是什么、实际发生了什么、为什么有差异、下次怎么做） | 复盘不是追责；一旦变成追责，大家就不说真话了 |

**F. 带人与团队**
| 场景 | 首选 | 何时换用 |
|---|---|---|
| 下属来求助，或需要辅导下属 | GROW（目标、现状、方案、意愿） | 下属能力很弱时，先直接指导，再用 GROW |
| 不同下属该用不同的领导方式 | 情境领导（按能力和意愿分四类，对应指令、教练、支持、授权） | 先用“意愿 × 能力”矩阵给员工分类 |
| 团队执行力差 | 管理 4C（布置清晰、真心承诺、辅导到位、全面控制） | 如果是团队协作出了问题，用 TOPIC 或团队协作五大障碍排查 |
| 团队协作不畅、互不信任 | 团队协作五大障碍（信任、冲突、承诺、责任、结果） | 按从下往上的顺序排查，信任是基础 |
| 员工积极性低 | 马斯洛需求层次、员工敬业度调查 | 先搞清是哪一层需求没满足，再对症下药 |
| 沟通总出问题 | 乔哈里视窗 | 用来扩大“公开区”，减少信息盲区 |

**G. 组织设计与变革**
| 场景 | 首选 | 何时换用 |
|---|---|---|
| 设计或调整组织架构 | 星型模型（战略、结构、流程、激励、人员） | 先用 consulting-analysis 的 7S 或六盒模型诊断问题在哪 |
| 推动一场全公司的变革 | Kotter 变革八步法 | 侧重组织层面的推进顺序 |
| 变革中员工个人跟不上 | ADKAR（认知、意愿、知识、能力、巩固） | 侧重个人层面，找出每个人卡在哪一步 |
| 判断变革的阻力有多大 | 力场分析（推动力 vs 阻力） | 变革启动前用 |
| 变革的整体节奏 | 勒温三阶段（解冻、变革、再冻结） | 最简单的变革框架，适合向团队解释 |

**H. 会议与集体讨论**
| 场景 | 首选 | 何时换用 |
|---|---|---|
| 需要大量新点子 | 头脑风暴 | 怕少数人主导或话题敏感时，用书面的 635 法 |
| 改进现有产品或服务 | SCAMPER | 要从零开始创新，用设计思维 |
| 讨论老是跑题、吵不出结论 | 六顶思考帽 | 同一时间所有人只用同一种思考方式 |
| 需要深入讨论、挖出潜在假设 | 深度汇谈 | 适合团队学习，不适合需要快速决策的场合 |

**选定方法后，先读对应的方法卡片再作答。** 在 `references/method-index.md` 末尾（个人方法在表格的“卡片”一列）找到对应的卡片文件，打开 `references/methods/` 下的这张卡片，把其中的操作步骤、输出模板和“常见误用”用进回答。选法表只告诉你用哪个方法，怎么用对要看卡片。

回答里只使用选定的主方法和辅助方法。不要顺手夹带第三个方法的规则；如果确实值得一提，就放在最后，作为“以后可以再加”的建议，并注明是哪个方法。

### 第三步：给出能直接用的产出

内部管理的产出应当拿来就能用。按场景给出对应的表格或清单：

- 目标：目标表（目标、关键结果或指标、负责人、截止时间、衡量方式）
- 计划与分工：任务表（事项、负责人、协助人、完成时间、交付物），或 RACI 表
- 问题：问题描述 → 原因分析 → 验证 → 对策表（临时措施、根本措施、负责人、期限）
- 复盘：目标与结果对比 → 亮点与不足 → 原因 → 规律与下一步行动
- 带人：谈话提纲（按 GROW 四步列出要问的问题）
- 变革：推进路线图（阶段、关键动作、负责人、衡量标志）

最后附一段简短的“方法说明”：用了什么方法、为什么选它、为什么没用相邻的方法。

## 几条底线

- 管理方法是为人服务的：团队成熟度低时，方法越简单越好，别一上来就推 8D、六西格玛。
- 每件事只有一个负责人。
- 目标必须能衡量；不能衡量的，至少要说清楚“做到什么样算完成”。
- 找原因不是找人背锅，要落到能改的流程和机制上。
- 方法说明要诚实：某个方法用在这里帮助不大，就直说。
