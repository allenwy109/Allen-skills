# 企业内部管理方法库

这里只管“有哪些方法、各自什么时候能用、怎么用对”。完整流程在能力层：`../core-framing/`、`../core-method-select/`、`../core-evidence/`、`../core-synthesis/`。用户只问一个方法时，也要先过 core-method-select 的前提检查。

内部管理的产出不是一份论证报告，而是一张能马上用的表：目标表、分工表、根因分析表、复盘记录、会议议程。选方法时特别看两件事：

1. **工作性质**：探索型（从 0 到 1，结果不确定）还是重复型（从 1 到 N，有标准）。这决定了 OKR 还是 KPI、PDCA 还是敏捷迭代。
2. **规模和成熟度**：个人、小组，还是跨部门、全公司。越正式、越跨部门，越需要结构化的方法（8D、方针管理）；团队成熟度低时，方法越简单越好。

## 和另外两个方法库的分工

- `lib-consulting` 回答“企业该往哪走、为什么经营成这样”。
- 本库回答“方向定了以后，怎么定目标、怎么执行、出了问题怎么查、事后怎么复盘、人怎么带”。
- `lib-personal` 回答“我自己怎么更高效”。

## 选法表

**情况**按问题性质找；**前提**缺了就不能用；**换用**写成“如果……→ 改用……”。

**A. 目标设定与分解**
| 情况 | 首选 | 前提 | 换用 |
|---|---|---|---|
| 检查单个目标写得好不好 | SMART | 目标已经定了，只是写法要检查 | 还没定该定什么目标 → OKR、平衡计分卡或目标多叉树 |
| 探索型、创新型工作，或自驱型团队 | OKR | 不和考核、奖金直接挂钩；员工有一定自主空间 | 文化高度依赖上级指令 → KPI；要挂钩考核 → KPI |
| 标准化、重复性工作的日常监控 | KPI | 结果可量化，有历史基线 | 需要鼓励突破 → 在 KPI 之上加 OKR |
| 公司战略要落成各层面的指标 | 平衡计分卡 + 战略地图 | 战略已经明确；企业相对成熟 | 初创企业、战略快速试错 → OKR |
| 多年战略要逐层分解到部门和个人 | 方针管理（Hoshin Kanri）/ OGSM | 战略周期长、方向稳定 | 环境变化快 → OKR |
| 大目标分解到具体事项 | 目标多叉树 | 大目标本身已定 | 目标还没定 → 先用 SMART、OKR 或平衡计分卡 |

**B. 计划与分工**
| 情况 | 首选 | 前提 | 换用 |
|---|---|---|---|
| 布置一项任务，怕漏掉要素 | 5W2H | 只有一项或少量任务 | 很多任务要排先后 → 四象限或优选矩阵；复杂项目 → WBS |
| 项目要拆成可执行的工作包 | WBS | 交付物和范围已经明确 | 需求不确定、常变 → 敏捷迭代 |
| 多人协作，职责不清、互相推诿 | RACI | 三人以上、多环节协作 | 两三个人的小事 → 口头说清即可 |

**C. 执行与持续改进**
| 情况 | 首选 | 前提 | 换用 |
|---|---|---|---|
| 有标准、可重复的工作，要越做越好 | PDCA | 工作可重复，有可衡量的标准 | 探索型、变化快 → 敏捷；严重质量或客诉问题 → 8D；需要严格数据证明 → DMAIC；只是事后快速总结 → AAR |
| 流程慢、浪费多 | 精益（八大浪费、价值流图） | 能画出流程、观察到现场 | 质量波动、需要统计分析 → 六西格玛；现场基础管理很乱 → 先做 5S / 6S |
| 质量波动大，需要用数据说话 | 六西格玛 DMAIC | 有基础数据，或有条件收集 | 问题简单、原因明显 → PDCA 或 5WHY |
| 现场脏乱、找东西费时间 | 5S / 6S | 问题确实在现场秩序 | 期望解决流程设计或战略问题 → 6S 做不到 |
| 不确定性高、需求常变的项目 | 敏捷迭代 | 团队能频繁沟通、快速决策 | 需求稳定、交付明确 → 传统计划和 WBS |

**D. 出了问题，找原因**
| 情况 | 首选 | 前提 | 换用 |
|---|---|---|---|
| 同时冒出很多问题，先解决哪个 | 优选矩阵 / 帕累托图 | 帕累托图需要按类别统计的数据 | 没有数据 → 优选矩阵打分 |
| 现象清楚，原因单一 | 5WHY | 问题已经发生；因果链比较清楚 | 原因多 → 鱼骨图；问题还没发生、要预防 → FMEA 类风险分析 |
| 原因多、涉及多个环节或部门 | 鱼骨图（制造业用 5M1E） | 问题已经发生；画完能拿数据验证 | 战略层面的问题（如份额下滑）→ lib-consulting 的议题树或 3C |
| 质量或客诉问题，要先止损再根治 | 8D | 问题严重、需要团队协作 | 小问题 → PDCA 或 5WHY |

**E. 复盘**
| 情况 | 首选 | 前提 | 换用 |
|---|---|---|---|
| 项目或阶段结束，正式复盘 | 复盘四步法 GRAI | 当初有目标可以回顾；目的不是追责 | 要解决一个具体质量问题 → 8D 或 PDCA；目的是追责 → 那不是复盘 |
| 会议或日常活动后快速总结 | 非正式 AAR（5 分钟） | 刚结束、大家都在 | 需要正式记录和改进 → GRAI |

**F. 带人与团队**
| 情况 | 首选 | 前提 | 换用 |
|---|---|---|---|
| 下属来求助，或需要辅导 | GROW | 下属有基本能力；情况不紧急 | 下属能力很弱 → 先直接指导（情境领导）；情况紧急 → 直接给指令 |
| 不同下属该用不同的领导方式 | 情境领导 | 能判断每个人的能力和意愿 | 问题出在整个团队协作 → 团队协作五大障碍或 TOPIC |
| 团队执行力差 | 管理 4C | 问题在执行环节，不在个别人或制度 | 个别人的问题 → 情境领导；组织结构或制度问题 → lib-consulting 的组织诊断 |
| 团队协作不畅、互不信任 | 团队协作五大障碍 | 团队成员相对固定 | 是领导方式问题 → 情境领导 |
| 员工积极性低 | 马斯洛需求层次、敬业度调查 | 能和员工谈或做调查 | 是领导方式不当 → 情境领导；是团队协作问题 → 五大障碍 |
| 沟通总出问题 | 乔哈里视窗 | 团队愿意互相给反馈 | 汇报没有条理 → 金字塔原理；个人冲突情绪 → lib-personal 的非暴力沟通 |

**G. 组织设计与变革**
| 情况 | 首选 | 前提 | 换用 |
|---|---|---|---|
| 设计或调整组织架构 | 星型模型 | 已经知道组织哪里出了问题 | 还不知道问题在哪 → lib-consulting 的 7S 或六盒模型；只是个别岗位调整 → 不必 |
| 推动一场全公司的变革 | Kotter 变革八步法 | 已经清楚要变什么 | 还没搞清楚要变什么 → lib-consulting 做诊断 |
| 变革中员工个人跟不上 | ADKAR | 能找到具体卡住的人 | 是组织层面推进顺序的问题 → Kotter |
| 判断变革的阻力有多大 | 力场分析 | 变革启动前 | —— |
| 向团队解释变革的整体节奏 | 勒温三阶段 | 需要简单易懂的框架 | 要具体的推进步骤 → Kotter |

**H. 会议与集体讨论**
| 情况 | 首选 | 前提 | 换用 |
|---|---|---|---|
| 需要大量新点子 | 头脑风暴 | 阶段内不评价 | 怕少数人主导或话题敏感 → 635 法；需要做决定 → 六顶思考帽或加权决策矩阵 |
| 改进现有产品或服务 | SCAMPER | 有一个现成的对象可改 | 从零开始创新 → 设计思维 |
| 讨论跑题、吵不出结论 | 六顶思考帽 | 有主持人能控制节奏 | 两三个人的简单讨论 → 不必这么正式 |
| 需要深入讨论、挖出潜在假设 | 深度汇谈 | 不急于做决定 | 需要快速决策 → 六顶思考帽 |

## 输出形态

内部管理的产出要拿来就能用。在 `../core-synthesis/` 的一页格式里，结论之后直接给对应的表：

- 目标：目标表（目标、关键结果或指标、负责人、截止时间、衡量方式）
- 计划与分工：任务表（事项、负责人、协助人、完成时间、交付物），或 RACI 表
- 问题：问题描述 → 原因分析 → 验证 → 对策表（临时措施、根本措施、负责人、期限）
- 复盘：目标与结果对比 → 亮点与不足 → 原因 → 规律与下一步行动
- 带人：谈话提纲（按 GROW 四步列出要问的问题）
- 变革：推进路线图（阶段、关键动作、负责人、衡量标志）

## 底线

- 管理方法是为人服务的：团队成熟度低时，别一上来就推 8D、六西格玛。
- 每件事只有一个负责人。
- 目标必须能衡量；不能衡量的，至少要说清“做到什么样算完成”。
- 找原因不是找人背锅，要落到能改的流程和机制上。
