# 审查

写的人很难看出自己的漏洞。审查由**没参与写作的独立子代理**来做，每个只管一个角度，并行跑。同一个代理换个角色名自己审自己，不算独立审查。

## 输入与输出

- 输入：任务文件夹里的 `00_brief.md`、`01_issue-tree.md`、`02_method-plan.md`、统一证据账 `03_evidence/`、`04_analysis/`、综合草稿；成品审查员另读 `08_deliverables/` 下的交付物。
- 输出：`05_review-log.md`（模板见 `assets/review-log-template.md`）；成品审查结论写进 `08_deliverables/acceptance.json`。

## 五个角色

| 角色 | 只查什么 | 给它什么（不给什么） | L2 | L3 |
|---|---|---|---|---|
| 事实核查员 | 对结论影响最大的 5 到 8 条事实，独立联网重查：过时、片面、虚假、口径 | 证据账（`03_evidence/`）+ 原始材料；**不给**结论的推理 | 开 | 开 |
| 红队（反方） | 最强的反对理由、其他解释、维持现状的基准、强词和过度推断 | 结论 + 支撑论点 + 证据账 | 开 | 开 |
| 方法审查员 | 每个子问题的方法选得对不对、前提是否满足、卡片里的常见误用有没有犯 | 问题拆解 + 方法计划 + 对应卡片路径 | — | 开 |
| 决策者视角 | 首屏能否读到答案；行动是否具体到人、时间、指标；有没有回答主导问题 | **只给**最终成品 `08_deliverables/report/` 的 PDF，不给过程 | — | 开 |
| 成品审查员 | 最终交付物的实际页面：身份是否如实、视觉是否有溢出截断遮挡和误读、中文是否完整、内容是否齐全 | **只给**最终交付物（PDF、PNG、PPTX、海报图片），不给过程文件和证据账 | 开 | 开 |

按深度开的角色数（深度的唯一标准在 router 第 2 节）：

| 深度 | 开哪些 | 共几个 |
|---|---|---|
| L1 | 不开子代理，作者按红队清单自查 | 0 |
| L2 | 事实核查员、红队、成品审查员 | 3 |
| L3 | 再加方法审查员、决策者视角 | 5 |

用了 core-research 并封包时，另开"研究包红队"审研究包。每个角色的任务提示词在 `references/reviewer-prompts.md`，照着填空后交给子代理。

成品审查员按 `references/output-standard.md` 的统一输出标准审查，结论写进 `08_deliverables/acceptance.json`（用 `<运行时>/tools/acceptance.py review`）。事实核查员、红队、方法审查员审的是分析和正文，在出成品之前；决策者视角和成品审查员审的是成品，在出成品之后。

## 怎么跑

1. **准备材料包**：按上表只给该角色需要的文件。不告诉审查者“这份已经不错了”，不给预期答案。
2. **并行启动子代理**：用当前环境的子代理工具（Claude Code 里是 Agent / Task 工具）为每个角色各开一个，互相看不到对方。每个设工具调用上限（事实核查员约 20 次，其余约 10 次）。
3. **收问题**：每条问题都要有级别（阻塞 / 重要 / 轻微）、位置、依据和建议改法。没有依据的意见降为“轻微”。
4. **修复**：阻塞和重要的问题必须修复，或写明不改的理由。修复后，只把改过的部分交给**原来提出问题的角色**复审一次。最多一轮复审，不无限循环。
5. **记录**：问题、处理结果、复审结论写进 `05_review-log.md`；报告附录 D 写一句“经过哪几种审查、改了什么”。

## 没有子代理能力时

按同样的角色清单依次自审，每个角色审完写下问题再进入下一个，并在报告附录 D 写明“**未经独立审查**，为作者按清单自审”。不要把自审写成独立审查。

## L1 快答

不开子代理。作者用红队清单快速自查一遍：最强的反对理由是什么？结论依赖的事实查过了吗？
