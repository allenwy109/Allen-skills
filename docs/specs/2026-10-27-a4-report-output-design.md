# A4 正式报告与演示稿双输出设计

日期：2026-10-27  
状态：独立对标审查后修订，待用户复核
适用仓库：Allen-skills

## 1. 背景与问题

Allen-skills 已具备研究、证据账、综合、故事线和正式验收能力，也完整引入了 `report-forge` 的 16:9/4:3 咨询型页面引擎。但当前 `out-report` 仍要求作者为每个任务临时编写 `pages.html` 与 `page.css`。这导致引擎能力与实际成品之间存在明显落差：桥接层虽完整保留多 panel，手写页面却可能没有全部渲染；布局和图表能力没有稳定复用，页面容易退化为重复卡片、无效留白和不可读脚注。

更根本的问题是媒介混用。深度研究报告需要 A4 连续阅读、真实分页、跨页表格、页眉页脚和高密度来源；融资路演需要 16:9 画布、单页单结论和演示节奏。两者不能继续共用同一套页面容量与排印规则。

本设计改造整个 Allen-skills 输出层，不针对某一次报告修补，也不依赖 entservice。

## 2. 目标与非目标

### 2.1 目标

1. 正式研究默认输出 A4 自包含 HTML 与同内容 PDF。
2. 按需输出 16:9 咨询型演示稿，并保持 `report-forge` 的成熟能力。
3. 所有场景共用同一份内容真源、证据身份和来源追溯。
4. 用确定性组件与有限布局系统稳定生成专业、克制、数据驱动的咨询报告。
5. 把排版美观作为正式门禁，而不只是检查文件是否成功生成。
6. 杜绝 panel、relation、claim、metric 或关键来源在输出转换中静默丢失。
7. 保持现有研究、证据、方法、综合和验收分层不变，只调整故事线到输出层的交接。

### 2.2 非目标

1. 不重写研究、事实核实、尽调或方法选择流程。
2. 不在第一阶段追求任意页面的无限自由排版。
3. 不把 entservice 的 renderer 作为运行时依赖。
4. 不删除或重写 vendored `report-forge`。
5. 不承诺一次生成即可免除人工成品审查。

## 3. 已确认的产品决策

1. 默认交付是 A4 阅读报告。
2. 16:9 路演稿按需生成。
3. `out-report` 与 `out-deck` 分离，各自采用适合媒介的分页、密度和视觉规则。
4. 两条输出链路共享证据账、主张、指标和故事线真源，不维护两份分析结论；媒介专属模型分别生成。
5. 默认视觉方向是国际咨询报告的编辑出版风格：浅色纸面、深灰正文、单一品牌强调色、克制装饰、强调结论和证据。
6. 上游 `consulting-report-forge` 的优秀演示页作为演示稿基准；A4 报告另建立经用户认可的黄金样板。

## 4. 总体架构

```text
证据账 + 07_storyline/slides.json
        │
        ├──→ 内容合同转换与完整性检查
        │             │
        │             ▼
        │    07_storyline/report.json
        │             │
        │             ▼
        │        out-report / A4 renderer
        │             │
        │             ▼
        │        A4 HTML + PDF
        │
        └──→ out-deck / report-forge
                      │
                      ▼
               16:9/4:3 HTML + PDF
```

`report.json` 是媒介无关的正式报告文档模型。它表达章节、内容块、证据关系和呈现意图，不包含像素坐标或具体 CSS。A4 renderer 确定连续阅读和打印排版。

第一阶段不让 deck 绕经 `report.json`：`out-deck` 继续从 `slides.json` 直接生成 deck blueprint，避免丢失 `story_beat`、`adds`、`density`、演讲意图和 deck 布局等媒介专属字段。两条链路共享证据账、claim、metric、source 和故事线真源，但各自做单向投影，不要求 A4 block 与 deck 页面一一对应。

## 5. 内容模型

第一阶段保留 `slides.json` 作为故事线真源，由确定性转换器生成 `report.json`，避免 `core-storyline` 同时维护两份文件。机器合同固定为 `tools/lib/schema/report.schema.json`，初始版本 `1.0.0`；模型文件固定在 `07_storyline/report.json`。schema 的破坏性修改必须升主版本，旧任务保留原解释并经显式迁移生成新文件，不能原地改写。

```text
report
├── metadata
├── executive_summary
├── sections[]
│   └── blocks[]
│       ├── finding
│       ├── prose
│       ├── metric
│       ├── chart
│       ├── comparison
│       ├── table
│       ├── evidence
│       ├── risk
│       └── recommendation
├── references
└── appendix
```

每个 block 至少保留：

- 稳定 ID 和所属章节；
- 支撑的 `claim_refs` 与 `metric_refs`；
- 来源 ID 与定位；
- 事实、估计、预测、假设、判断或建议身份；
- 对应的 panel、角色、关系和展示意图；
- 组件容量所需的结构化数据；
- 与相邻 block 的比较、递进、拆解或总览—细节关系。

schema 必须定义 block 枚举、必填字段、ID 唯一性、引用完整性、允许的嵌套、来源身份和版本兼容策略。实施计划必须另附逐字段映射表，不能只靠示例推断。

转换器必须生成 `coverage-manifest.json`，对输入和输出做集合级比较，而不是只比较计数：正文关键 claim、A 级证据、全部 panel、panel relation、正文引用的 metric 和关键来源必须集合相等；重复、孤儿或未知引用均失败。现有 `to_forge.py` 已能完整搬运和校验多 panel，风险发生在作者手写页面没有把全部 panel 渲染出来；新 renderer 必须从覆盖清单逐项消费，不能只取第一个 panel，也不能用普通文字框静默代替未支持内容。

未支持的 block、关系、容量和引用问题使用稳定错误码，例如 `REPORT_UNSUPPORTED_BLOCK`、`REPORT_COVERAGE_MISMATCH`、`REPORT_CAPACITY_HARD_LIMIT`，测试断言错误码而不是易变的提示文案。

## 6. A4 页面与视觉系统

### 6.1 页面基础

- A4 纵向，MediaBox 为 210 × 297 mm；实现测试允许每边不超过 0.2 mm 的测量误差。PDF 使用真实分页；HTML 显示同一组 A4 页面并提供章节导航。
- v1 使用单一权威主题。基础页边距为上 18 mm、外 17 mm、下 18 mm、内 20 mm；无装订用途时仍沿用内外边距以保持双页节奏。来源区包含在正文框内，不能侵入页脚。
- 正文使用批准并嵌入的中文无衬线字体，10.75pt/17pt；一级标题使用批准的中文衬线字体，20pt/27pt，最多两行；二级标题 14pt/20pt；图表与表格正文不低于 8.5pt/12pt；来源不低于 7.5pt/10pt。最终字体家族和字重随黄金小册一起冻结，之后更换视为视觉基准变更。
- 正文单栏每行目标 34–42 个中文字符；双栏每栏 22–29 个。采用 4.25pt 基线步长，正文、注释和表格尽量回落到基线网格。
- 数字使用 tabular figures；表格数字右对齐，小数按小数点对齐；单位置于列标题或图表口径，不在单元格逐项重复。
- 标题不得单独留在页底；标题与后续至少两行正文或对应展品黏连。正文避免首行孤行与末行寡行；图题不得与图分离，表题与表头不得跨页分离。
- CJK 标点、禁则和 URL 断行必须有固定测试；长 URL 优先显示短标签并保留完整可点击链接。
- 不允许通过缩放整页或低于可读阈值的字体解决容量问题。
- 字体本地嵌入，并明确中文、英文、数字和等宽内容的 fallback。
- 页面在彩色、灰度、屏幕和打印环境下均可区分状态。

### 6.2 A4 Layout Atlas

组件描述“内容是什么”，布局描述“证据关系怎样转化为空间”。两者不得混为一层。A4 renderer 必须有独立的 `layout-atlas/catalog.json` 和可视化 atlas；v1 至少覆盖：

1. 全幅主证据；
2. 主图 + 右侧解读栏；
3. 图 + 精确数据表；
4. 双栏并列比较；
5. 小多图或同尺度分面；
6. 2×2 决策矩阵；
7. 流程或路线图；
8. 长文 + 旁注或证据引文；
9. 跨页长表；
10. 总览—细节连续页。

每个布局条目必须冻结：`reader_task`、`reading_path`、主辅比例、允许的 block/panel 组合、soft/hard capacity、tradeoff、avoid、拆页策略和留白职责。布局选择必须从真实证据关系出发；换配色、微调尺寸或给相同卡片改名不算新布局。

### 6.3 首批组件

第一版只实现高频且能覆盖现有场景的 12 类组件：

1. 封面；
2. 目录；
3. 执行摘要；
4. 章节标题；
5. 核心结论与证据；
6. 数据图表；
7. 竞品或方案比较；
8. 客户痛点与需求强度；
9. 市场规模与趋势；
10. 风险、反证与边界；
11. 建议与路线图；
12. 来源和附录。

组件不是装饰模板，而是语义与排版合同。每类组件定义允许的 block、视觉层级、可用布局、容量维度、拆页策略和失败条件。

### 6.4 视觉规则

- 每页有明确的视觉入口、主要结论、主证据和次要说明。
- 主展品的面积和对比度与证明责任匹配。
- 结论、证据、限制和来源不能竞争同一视觉层级。
- 表格强调数字对齐、单位一致、重点行列和跨页表头，减少粗重边框。
- 图表统一色盘、坐标轴、直接标签、预测/估算样式、注释和来源区。
- 色彩用于表达含义，不使用大面积深色卡片、浮夸渐变、玻璃效果或装饰性图标填白。
- 章节页、分析页、比较页、图表页和行动页形成整册节奏；变化服务于叙事，不为凑类型机械换版。
- 留白必须承担分组、强调、阅读停顿或来源安全区功能。
- 每页只能有一个一级视觉焦点。标题、副标题、主展品、takeaway 和侧栏必须服务同一页结论，不能各自下一个判断。
- 主展品应获得页面正文可用面积中最大的连续区域，并在面积、位置或对比度上形成可解释优势；人工验收必须确认第一眼落点等于声明的主证据。
- 图片、照片、logo、地图和网页截图不纳入 v1 的自由内容组件。确有证据需要的截图只能作为带来源、时间、裁切说明和可读原件链接的 evidence block，不能用作装饰。

### 6.5 图表视觉语法

建立独立 form catalog，把证据关系映射到优先图型和禁用图型。每个 form 必须定义：允许的 relationship、共同基线和排序规则、直接标签、最小绘图区、单位与期间、annotation、缺失/零/负值、实际/估计/预测/目标的线型与填充、soft/hard capacity 和灰度冗余。

- 比较默认使用共同零基线；截轴必须显式标注且通过人工审查。
- 能直接标注时不使用图例；图例不得迫使读者来回匹配超过 5 个系列。
- 预测使用虚线或空心标记，估计和目标拥有不同的文字或线型冗余，不能只靠颜色。
- 排名图按数值排序；时间序列按时间顺序；矩阵逐格给出依据。
- 自定义 SVG 仍可使用，但必须声明 semantic type、原始数据、容量和渲染合同，并通过相同 QA。
- 图表和表格都必须带主体、期间、单位、身份、注释与来源；这些信息顺序固定为题目/口径 → 图表主体 → 注释/限制 → 来源。

### 6.6 容量与分页

每类组件定义可测试的容量上限，例如表格列数和行数、比较对象数量、图表标签数、正文字符量和来源数量。超过上限时按以下顺序处理：

1. 在保持语义关系的前提下拆成连续页面；
2. 将细节移入附录并在正文建立明确引用；
3. 改用更适合容量的组件；
4. 无法安全处理时构建失败。

禁止缩小字体、压扁行距、截断来源或溢出页面。

### 6.7 连续阅读与装订规则

- 封面、目录、章节开篇和封底不显示常规页眉；正文页显示报告短名与章节。
- 新章节优先从 recto 开始；若因此产生空白页，必须是显式结构页并从页数和目录规则中正确处理，不能出现匿名空白页。
- 图表原则上不跨页；长表允许跨页并重复表头，显示“续表”及当前范围。
- 脚注与对应正文同页；来源清单可跨页，但条目不得从标签与 URL 中间任意断开。
- 目录页码在最终分页后生成；HTML 导航锚点与 PDF 页码写入同一 `pagination-manifest.json`。
- 章节末不得留下仅有少量正文的孤页；算法无法安全重排时要求作者拆分或合并 block。

### 6.8 整册 Art Direction

每章应形成“开篇定向 → 证据展开 → 综合或停顿 → 决策收束”的节奏，但不强迫证据不足的章节凑齐页型。连续页面使用同一骨架时必须具有共同量尺、对象对照或稳定阅读路径等具体理由；否则回到 layout atlas 重选构图。

正式审查必须生成全册 contact sheet、逐章 contact sheet、标题链和布局/form inventory。审查者同时在缩略图尺度检查节奏与重心，在 100% 尺度检查排印、标签和来源；不得以布局数量达到某个配额代替真实画面判断。

## 7. 渲染职责

AI 负责：

- 选择语义组件；
- 决定内容并列、拆解或递进关系；
- 指定主证据和阅读路径；
- 在有限布局集合中说明选型理由。

确定性渲染器负责：

- HTML 结构；
- 字体、间距、网格、颜色和排印；
- 分页与跨页行为；
- SVG 图表和表格表现；
- 页眉、页脚、页码、来源和附录；
- 容量检查与自动拆页。

特殊定制页只作为显式扩展插槽存在，不是默认生产路径，也不能绕过内容绑定与视觉验收。

### 7.1 A4 renderer 技术合同

v1 使用仓库锁定版本的 Playwright Chromium、内嵌字体和无外部网络资源的 HTML/CSS/SVG。分页采用“两阶段确定性分页”，不把浏览器一次打印的偶然换页当成合同：

1. 在固定 viewport、device scale、字体和 Chromium revision 下测量 block；
2. 按 layout capacity 与实测高度生成显式 A4 page DOM；
3. 对跨页表格生成重复表头和续表标识；
4. 生成页码、目录和 `pagination-manifest.json` 后第二次渲染；
5. 每个 `<section data-page-id>` 对应一个 PDF 页面，再用打印 CSS 导出。

最终 HTML 与 PDF 共用同一显式分页 DOM。PDF 允许创建时间等元数据不同，但页数、MediaBox、文本清单、内容覆盖和几何摘要必须一致。自包含 HTML 只允许内联 CSS/SVG、data URL 和仓库批准的内嵌字体；不允许运行时外部请求。

## 8. 双输出链路

### 8.1 `out-report`

`out-report` 改为 A4 正式报告入口：

1. 检查故事线和证据账；
2. 生成并校验 `report.json`；
3. 选择组件与有限布局；
4. 渲染自包含 HTML；
5. 用浏览器打印生成 A4 PDF；
6. 执行机械、几何、内容与视觉验收；
7. 独立成品审查后登记交付。

不再要求作者为每项任务从零编写完整 `pages.html` 与 `page.css`。

### 8.2 `out-deck`

新增 `out-deck`，承接现有 `report-forge`：

- 输出 16:9 或 4:3 HTML 与 PDF；
- 继续使用上游布局图谱、图表形式、执行清单和审查合同；
- 保证页面作者完整渲染桥接层已经保留的全部 panel 与 relation；
- 恢复上游展示样板和黄金截图，防止“引擎存在、实际不用”；
- 只有用户明确需要路演、汇报或演示稿时触发。

`out-report` 与 `out-deck` 共享来源、指标、证据身份和内容覆盖检查，但不共享页面 CSS、容量阈值和媒介验收规则。

迁移不得降低以下锁定能力：38 个 layout（30 个正文与 8 个首尾/结构布局）、6 个 master、`mckinsey`/`bcg`/`accenture` 三主题、16:9 与 4:3 两种比例、完整 form-capacity catalog，以及 narrative、composition、module-fill、review-reuse、execution-plan 合同。若后续主动删除任何能力，必须单独设计并获得用户确认。

官方 showcase 的批准子集、构建脚本和截图 manifest 应按明确的上游 commit、许可证、文件 hash 纳入 vendor lock 或独立 visual-baseline lock。上游同步不得自动覆盖已批准基准，必须生成差异审查记录。

## 9. 失败与降级

- 内容超出容量：拆页；无法安全拆分则报错。
- 图表缺少结构化数据：退化为证据表或文字分析并记录原因，不虚构数据。
- 字体、浏览器或 PDF 依赖缺失：停止正式 PDF 交付；HTML 只能标记为预览。
- 溢出、遮挡、异常空白、不可读来源或关键内容裁切：验收失败。
- 内容覆盖检查发现丢失：构建失败。
- 独立视觉审查未完成：只能交付预览，不能写成正式完成。
- 旧任务可读取；重新生成时明确声明采用新版 A4 输出。若仍需要旧版 deck，改走 `out-deck`。

## 10. 质量门禁

正式报告必须依次通过：

1. **内容完整性**：关键 claim、A 级证据、panel、relation、metric 和来源均被覆盖。
2. **证据一致性**：数字和身份来自证据账，未核实内容不得伪装成事实。
3. **机械排版**：无溢出、遮挡、孤行、断裂表格、异常空白页或不可读来源。
4. **组件容量**：全部组件处于允许范围，超限已经拆页或构建失败。
5. **整册视觉**：层级、平衡、对齐、密度、节奏、图表表达和专业感达到基准。
6. **黄金样板**：关键组件的截图与批准基准没有未解释的明显退化。
7. **最终媒介**：HTML 与 PDF 均实际打开检查，内容与页序一致。
8. **独立审查**：没有未解决的 Blocking 或 Major 问题。

自动流程应从最终 PDF 选出最密页、最大空白页、最复杂图表页、来源最多页和最强结论页，要求审查者查看实际截图。自动检查只能定位问题，不能替代对美感与可理解性的判断。

正式视觉签署不能只抽查上述五类页面：审查者必须逐页查看最终 PDF、逐章查看 contact sheet、连读标题链，并在 100% 与缩略图两种尺度下检查。记录必须写具体所见、修复或接受理由，泛化的“正常”“PASS”无效。

自动检查和人工判断分别落盘：机器证据写入 geometry、coverage 和 regression manifest；人工判断写入 visual review，二者不能互相冒充。各检查的名称、版本、证据文件和状态映射到 `acceptance.json.upstream_checks`；人工接受的非阻塞差异写入 dispositions。

## 11. 测试策略

### 11.1 契约测试

- `slides.json → report.json` 的字段映射；
- 多 panel、多 relation 和 anchor panel 完整保留；
- claim、metric、来源和身份覆盖；
- 丢失或未支持内容时失败；
- 同一输入产生稳定输出。

### 11.2 组件测试

- 12 类组件的最小、正常、临界和超限样本；
- 中文、英文、数字、长 URL 和长来源；
- 自动拆页、附录迁移和失败行为；
- 表格跨页表头、图表标签和直接注释。

### 11.3 PDF 几何测试

- A4 页面尺寸和页边界；
- 页眉页脚和页码；
- 溢出、裁切、重叠、孤行和空白页；
- 图表、表格和来源安全区；
- HTML 与 PDF 内容清单一致。

### 11.4 黄金截图测试

实现 tokens 和完整组件库前，先制作并由用户确认一份 12–20 页真实“黄金小册”，至少包含封面、目录、执行摘要、章节开篇、定量图表、图+表、竞品矩阵、文字证据、风险、建议路线图和多页来源。先从成册效果反推 tokens、layout atlas、组件和容量，不能先固化工程结构、最后再补审美基准。孤立组件截图只能辅助调试，不能证明整册节奏。

基准环境固定 Playwright Chromium revision、内嵌字体 hash、viewport、device scale、PDF 导出参数和 144 DPI PDF rasterization。`visual-baseline.json` 保存环境、输入 fixture、页面 hash、批准人、批准时间和变更理由。像素或感知差异用于发现变化，不直接证明美感；超阈值必须由设计审查判定“退化”或“有意改善”，基准不得自动更新。

黄金 fixture 必须包含长中文标题、双语、长来源或 URL、密表、稀疏结论、极端标签、跨页表和灰度打印。HTML 与 PDF 分别保留基准。

### 11.5 场景验收

首批样本覆盖创业点子评估、企业全景分析、BP 评审、行业研究、定量图表密集报告和文字证据密集报告。不能只用当前 AIDC 案例证明系统有效。每类至少有一个固定正例和一个关键负例，并锁定输入快照、fixture ID、预期 coverage 集合、组件集合、页数范围、审查状态和基准 hash。

固定输入连续运行至少三次：`report.json` 字节一致，normalized HTML、coverage manifest 和 pagination manifest 一致；PDF 可忽略元数据，但页面尺寸、页数、文本清单和几何摘要必须一致。

### 11.6 与参考仓库的视觉对标

“达到或超过参考仓库”采用匿名 A/B 人工对标，不采用作者自评分。A4 与 deck 分开比较：deck 对照官方 showcase；A4 对照已批准黄金小册及从官方 showcase 提炼的构图质量。

独立审查者按 1–5 分并给出页面证据，维度为：视觉焦点、证据—几何匹配、信息密度、排印精度、图表清晰度、跨页节奏、来源整合、整体完成度。每个维度在黄金小册中保存 1/3/5 分锚点示例。

通过条件：

- 匿名 A/B 中，新成品总体判断“不劣于”批准参考；
- 八个维度均不低于 4/5；
- 没有未解决的 Blocking 或 Major；
- 第一眼落点与声明主证据一致；
- 逐页、逐章和整册三种尺度均完成审查。

像素回归、布局计数和自动几何检查均不能替代该门禁。

## 12. 完成标准

本改造只有同时满足以下条件才算完成：

1. 所有正式研究入口默认生成 A4 HTML/PDF。
2. A4 HTML 与 PDF 可连续阅读，内容、来源和页序一致。
3. 关键内容没有从故事线到成品的静默丢失。
4. 代表组件达到用户确认后的黄金样板。
5. 六类场景样本均通过契约、组件、几何和视觉验收。
6. `out-deck` 保留 16:9 咨询演示能力，并达到上游示范的视觉基准。
7. 两条输出链路均没有未解决的 Blocking 或 Major 成品问题。
8. 仓库安装、自检、文档与统一验收均反映新的输出架构。

其中“达到视觉基准”不能由文件生成成功、像素差或作者自评替代，必须通过第 11.6 节的匿名对标。

## 13. 实施边界与顺序

该设计适合一个实施计划，但应分阶段交付：

1. 冻结参考仓库能力清单，恢复 showcase 子集，建立视觉评分锚点；
2. 制作并由用户批准 A4 黄金小册；
3. 建立 `report.json` schema、逐字段映射、转换器和内容覆盖检查；
4. 从黄金小册提炼并冻结 A4 design tokens、排印合同、layout atlas 和 form catalog；
5. 实现首批组件、两阶段分页、HTML/PDF 和几何检查；
6. 改造 `out-report`，接入机器证据、逐页人工审查和统一验收；
7. 新增 `out-deck`，把现有 report-forge 链路迁入并跑完整能力矩阵回归；
8. 建立视觉回归、匿名 A/B 对标和多场景验收；
9. 更新安装、架构、场景路由和用户文档。

每一阶段都应先写失败测试，再做最小实现；不得在同一阶段顺带重构研究或证据系统。
