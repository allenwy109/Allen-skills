# 设计：创业点子与技术企业化前景评估应用

- 日期：2026-10-27
- 状态：用户已确认对话设计，待用户审阅书面规格
- 范围：Allen-skills 新增 `allen-idea` 应用入口、`scene-idea` 场景及其运行时接线

## 1. 背景与目标

现有四个企业应用都以已经存在的企业或 BP 为对象。用户只有一个创业想法或一项技术时，尚不存在可供尽调的企业主体、经营数据和完整商业计划书；直接套用 `allen-company` 会混淆事实与假设，直接套用 `scene-topic` 又不足以完成企业化路径设计与比较。

本次新增独立应用 `allen-idea`。它通过多轮提问澄清想法或技术，构造 2–3 种合理的企业化落地路径，验证真实痛点、需求强度、竞品与替代方案，分别推演短期、中期和长期发展前景，最后交付正式报告并给出决策等级或发展方向建议。

本应用回答的问题是：

> 如果把这个想法或技术按几种合理方式落地为企业，各自的发展前景如何；它是短期窗口、稳定现金流、长期复利机会、高风险规模赌注，还是缺乏真实需求的伪机会？

## 2. 已确认的产品决定

| # | 决定 |
|---|---|
| D1 | 新建独立应用，不把未成立企业塞进 `allen-company` |
| D2 | 先多轮澄清想法或技术，再开始正式研究 |
| D3 | 同一技术存在多种用途时，并列比较 2–3 种企业化路径，不静默选择一种 |
| D4 | 真实痛点、需求强度、竞品和潜在竞品是核心判断，不以市场规模代替需求验证 |
| D5 | 首版验证需求意愿和强度，不要求已有订单或完成客户访谈；没有付费证据时必须明确标注 |
| D6 | 分别判断短期、中期和长期市场前景，并判断是快钱还是值得长期经营 |
| D7 | 最终给出决策等级或发展方向建议，并提供下一阶段最小验证实验 |
| D8 | L2、L3 交付 HTML + PDF 主报告及 supporting-package.zip，沿用现有统一验收 |

## 3. 边界

### 3.1 本次范围

- `allen-idea` 应用 Skill、Codex/Claude 入口和系统提示词；
- `scene-idea` 场景 Skill；
- 想法定义卡和路径比较表模板；
- `app_runtime.py` 对 `allen-idea`、访谈等待和用户确认的支持；
- router、安装器、README、INSTALL、ARCHITECTURE 和验证脚本的必要接线；
- 与新入口相关的自动测试和方法选择用例。

### 3.2 不在本次范围

- 新建独立评分引擎或数据库表；
- 自动联系潜在客户、发送问卷或代表用户开展商务活动；
- 把情景推演包装成精确财务预测；
- 替代正式的法律、财税、专利或监管意见；
- 修改现有四个企业应用的语义。

## 5. 运行流程与状态

### 5.1 阶段顺序

```text
intake
→ clarify
→ pathing
→ framing
→ research
→ method
→ analysis
→ review
→ synthesis
→ storyline
→ report
→ support
→ acceptance
```

各阶段职责：

| 阶段 | 目标 | 必需产物 |
|---|---|---|
| intake | 保存用户原始要求，接收附件或网址 | `00_brief.md`、项目记录 |
| clarify | 多轮澄清想法、技术、客户、场景、资源和约束 | `00_idea-definition.md` |
| pathing | 构造并确认 2–3 种企业化路径 | `00_venture-paths.md` |
| framing | 为路径比较建立主导问题和子问题 | `01_issue-tree.md` |
| research | 验证需求、竞品、市场时机和外部事实 | `03_evidence/`、`03r_research/` |
| method | 为各子问题选择方法并检查前提 | `02_method-plan.md` |
| analysis | 比较路径并推演假想企业 | `04_analysis/` |
| review | 事实核查、红队和成品审查 | `05_review-log.md` |
| synthesis | 决策等级、方向和最小验证实验 | `06_synthesis.md` |
| storyline–acceptance | 沿用现有正式报告、支撑包和验收流程 | `07_storyline/`、`08_deliverables/` |

`research` 放在 `method` 前，是因为市场是否存在、需求证据是否足够、竞品数据是否可得，会决定后续方法能否成立。方法阶段仍可把发现的新缺口送回研究阶段。

### 5.2 多轮澄清

每轮只问最影响结论且用户尚未回答的问题。至少澄清：

- 想法或技术实际能完成什么；
- 谁在什么场景下遇到什么问题；
- 当前如何解决以及付出什么成本；
- 用户认为现有方案哪里不足；
- 目标地域、行业和客户类型；
- 创始人已有的技术、渠道、资金、团队和行业资源；
- 哪些约束不能改变，哪些落地方式可以调整。

当信息足以形成企业化假设时，生成 `00_idea-definition.md`，清楚分为：

1. 用户已确认的信息；
2. 系统为了继续分析提出的假设；
3. 仍未知、可能改变结论的问题。

在用户确认前，运行状态为 `waiting_user`，不得进入正式研究。用户确认写入证据账 `reviews` 表，类型为现有 `user_confirmation`，`covers.files` 包含 `00_idea-definition.md`；`app_runtime` 同时检查文件和该确认记录，只有两者都存在才能推进 clarify。

### 5.3 企业化路径

通常构造 2–3 条实质不同的路径。每条路径必须明确：

```text
目标客户 → 使用场景 → 核心产品 → 价值主张
→ 收费方式 → 获客方式 → 关键能力 → 主要假设
```

路径之间必须在客户、场景、产品形态、商业模式或进入方式上至少有一项关键差异，不能只是换名称。生成 `00_venture-paths.md` 后让用户确认；确认记录同样使用 `user_confirmation`，`covers.files` 包含该文件。用户没有偏好时仍保留全部路径进入研究，不提前选赢家。

## 6. 真实痛点与需求强度

### 6.1 证据梯度

需求证据按其实际能证明的程度使用：

1. 客户主动抱怨、搜索或寻求帮助；
2. 客户投入时间、人力或变通成本；
3. 客户采购、招标、招聘或自建解决方案；
4. 客户持续使用并支付竞品或替代方案；
5. 客户更换方案、追加预算或主动要求更好的产品。

每条路径还需判断需求的频率、严重性、紧迫性、受影响人数、决策权限和预算来源。

### 6.2 证据边界

- 搜索量、社交媒体热度、点赞、媒体报道和宏观市场规模不能单独证明需求强度；
- 公开投诉和讨论可以证明问题存在，但不能自动证明购买意愿；
- 招聘、招标、预算、采购和持续付费是更强信号，但仍要核对其适用客户和场景；
- 没有访谈、订单或采购证据时，不得写“付费意愿已验证”；
- 公开证据不足不阻止交付，但相应结论标为“未证实”并降低置信度。

报告用“强 / 中 / 弱 / 未证实”表达需求强度，同时列出支持证据、反面证据、关键未知项和最可能改变判断的新证据。

## 7. 竞品与潜在进入者

竞品检索从“客户在具体场景下如何解决问题”出发，不只搜索与想法同名的产品。每条路径建立独立竞争地图，覆盖：

1. 直接竞品：相近客户、问题和产品；
2. 间接竞品：不同技术或服务解决同一问题；
3. 现状替代：人工、表格、外包、内部系统和“不处理”；
4. 邻近进入者：已有客户、渠道、数据或技术能力，可能低成本进入的企业；
5. 潜在新进入者：科研成果、开源项目、新融资团队、专利方向和大厂新产品。

研究信号包括客户采购、招投标、招聘、应用目录与评价、行业会议、协会与渠道目录、融资新闻、专利、论文、开源项目、客户论坛和大企业产品更新。

竞品表至少比较：目标客户、场景、价值主张、产品形态、价格或收费方式、获客渠道、成熟度、证据强度，以及进入本市场的能力。无法确认的信息保留为空或标为未知，不推测填充。

分析必须回答：

- 市场空白是机会，还是需求太弱导致无人进入；
- 哪些参与者最可能快速复制或压制该路径；
- 该路径能建立什么差异化，差异能否积累为防御能力。

## 8. 时间前景与机会类型

默认时间窗口：

- 短期 0–2 年：需求是否已经发生、成交和回款速度、定制依赖、政策或供需窗口；
- 中期 3–5 年：市场扩张、标准化、复购、规模经济、竞争加剧和行业整合；
- 长期 5–10 年：结构性需求、技术替代、产业变化、平台/数据/渠道壁垒。

每条路径分别评价：市场时机、快速变现、增长持续性、可规模化、防御能力、替代风险、资源要求和资本适配。

综合后归入以下机会类型之一：

- 窗口型快钱；
- 现金流生意；
- 长期复利型；
- 高风险规模赌注；
- 伪机会。

类型是对证据和情景的综合判断，不是固定分数映射。报告必须解释为什么，并说明哪些假设变化会导致类型改变。

## 9. 决策输出

最终决策等级为：

- 值得推进；
- 有条件推进；
- 建议调整方向；
- 暂不建议。

决策可以针对某条路径，不要求给整个技术一个笼统结论。推荐路径还需给出：

- 短期进入方式；
- 中期扩张所需条件；
- 长期护城河要求；
- 下一阶段最小验证实验；
- 实验的成功、失败和停止标准；
- 最可能推翻当前结论的证据。

## 10. 主报告结构

1. 执行摘要；
2. 想法与技术定义；
3. 2–3 种企业化路径；
4. 真实痛点与需求强度；
5. 市场边界、驱动因素与进入时机；
6. 竞品、替代方案与潜在进入者；
7. 路径横向比较；
8. 各假想企业的短、中、长期前景；
9. 决策等级与发展方向；
10. 下一阶段最小验证实验；
11. 证据、假设、局限与参考来源。

报告不得编造精确营收、估值或份额。数据足够时可以给区间或情景测算，并明确输入、计算方法和敏感变量。

L2、L3 默认交付：

1. `08_deliverables/report/` 中的同版 HTML 和 PDF；
2. `08_deliverables/supporting-package.zip`；
3. `08_deliverables/acceptance.json` 中分别登记并验收。

## 11. 失败与回退

- 想法定义不足：保持 `waiting_user`，继续问一个最关键问题；
- 用户拒绝补充：以明确假设继续，但在报告中提高不确定性；
- 不能形成两条实质不同路径：说明原因，只评估一条，不制造伪选项；
- 研究发现原始客户或场景不成立：返回 pathing 阶段，建议替换客户、场景或商业模式；
- 竞品信息不足：标注未知，给出需要人工验证的名单和方法；
- 渲染依赖不通过：沿用现有规则，先交综合稿和故事线，不用其他工具伪造正式报告；
- 任一验收项失败：不得把应用标为 completed。

## 12. 实现改动

| 对象 | 改动 |
|---|---|
| `allen-idea/` | 新应用入口、固定场景、覆盖要求、交付契约 |
| `scene-idea/` | 澄清、路径构造、需求/竞品/时间前景分析编排 |

| `tools/tests/test_app_runtime.py` | 新应用顺序、确认门禁、回退和完成条件 |
| `router/SKILL.md` | 把创业想法/技术路由到 `allen-idea`，不误分到公司或普通话题 |
| `commands/*`、`install.sh` | 安装第五个应用入口 |
| `README.md`、`INSTALL.md`、`ARCHITECTURE.md` | 产品说明、调用方法和架构更新 |
| `tools/validate.py`、相关测试 | 确认入口、应用资产、跨 Skill 引用和安装结果完整 |

不修改统一证据账 schema；所需的假设、主张、证据、冲突、缺口和用户确认均能使用现有表表达。

## 13. 测试与验收

### 13.1 行为基线与 Skill 前向测试

在编写 Skill 前，用不加载 `allen-idea` 的独立测试场景记录基线，至少覆盖：

1. 一句话模糊想法；
2. 同一技术有多个应用方向；
3. 市场热度高但缺少购买信号；
4. 直接竞品很少但替代方案强；
5. 短期政策窗口强、长期可防御性弱。

基线应暴露当前系统是否过早下结论、只找同名竞品、把市场规模当需求、或把假设写成事实。实现后用同一组场景验证行为改变。

### 13.2 自动测试

- `app_runtime` 能创建并推进 `allen-idea`；
- 未确认想法定义卡时不能越过 clarify；
- 未确认路径时不能越过 pathing；
- research、analysis、review、support 和 acceptance 的必需产物门禁生效；
- 安装脚本同时安装 Skill 和 Claude/Codex 入口；
- validate 检查所有跨 Skill 引用和应用资产；
- 现有四个应用的阶段顺序和行为不回归。

### 13.3 内容验收

- 模糊想法先澄清，不直接报告；
- 能形成并比较 2–3 条实质不同路径；
- 能发现不同名称和技术路线的竞品、替代方案及潜在进入者；
- 没有付费证据时不声称付费意愿已验证；
- 每条路径分别给出短、中、长期前景；
- 明确机会类型、决策等级、发展方向和最小验证实验；
- 用户信息、系统假设、外部事实和推演结论在报告中可区分；
- HTML、PDF 和支撑包通过统一 acceptance。

## 14. 完成定义

只有同时满足以下条件才算实现完成：

1. 新入口在 Claude Code 和 Codex 安装后可发现；
2. Skill 前向测试显示预期行为，相同基线问题不再出现；
3. 自动测试和 `tools/validate.py` 通过；
4. 用一个虚构创业想法跑通从澄清到 acceptance 的端到端夹具；
5. 现有四个应用无回归；
6. 文档与实际命令、文件名和阶段顺序一致。
