# 创业点子场景

## 先澄清

从 `assets/idea-definition-template.md` 建立 `00_idea-definition.md`。已知内容不重复问；每轮只问一个最影响结论的问题。至少澄清技术或想法、客户与场景候选、当前做法与成本、创始人资源、地域范围和不可改变的约束。

明确区分用户已确认的信息、系统分析假设和仍未知的问题。内容不足时用 app_runtime `wait`，理由写明当前最关键的问题。用户确认定义卡后，运行 app_runtime `confirm <任务目录> --file 00_idea-definition.md`，再 `resume` 和推进。确认绑定文件摘要；确认后修改文件必须重新确认。

## 企业化路径

从 `assets/venture-paths-template.md` 建立 `00_venture-paths.md`，通常保留 2–3 条路径。每条明确目标客户、使用场景、核心产品、价值主张、收费方式、获客方式、关键能力和主要假设。

路径必须在客户、场景、产品形态、商业模式或进入方式上至少有一项关键差异。确实只有一条合理路径时记录原因，不制造伪选项。用户确认后运行 app_runtime `confirm <任务目录> --file 00_venture-paths.md`。

## 研究要求

先用 `../core-framing/` 建问题树，再用 `../core-research/` 和 `../core-evidence/` 研究每条路径。需求强度检查问题发生频率、严重性、紧迫性、受影响人数、现有投入、决策权限和预算来源。按证据只能写“强 / 中 / 弱 / 未证实”，同时列支持证据、反面证据、未知项和最可能改变判断的新证据。

竞品检索从客户问题和现有做法出发，必须覆盖：

1. 直接竞品：相近客户、问题和产品；
2. 间接竞品：不同技术或服务解决同一问题；
3. 现状替代：人工、表格、外包、内部系统和“不处理”；
4. 邻近进入者：已有客户、渠道、数据或技术能力的企业；
5. 潜在新进入者：科研成果、开源项目、新融资团队、专利方向和大厂新产品。

至少比较目标客户、场景、价值主张、产品形态、价格或收费方式、获客渠道、成熟度、证据强度和进入本市场的能力。回答市场空白是机会还是需求弱、谁最可能复制或压制该路径、差异能否积累为防御能力。

研究发现原路径的客户或场景不成立时，运行 app_runtime `rewind <任务目录> --stage pathing`，修改 `00_venture-paths.md` 并重新取得用户确认；不得手工改 `app-run.json` 或带着失效路径继续。

## 分析与时间前景

用 `../core-method-select/` 从 `../lib-consulting/` 为子问题选方法，再把分析写入 `04_analysis/`。每条路径分别评价：

- 短期 0–2 年：已发生需求、成交回款、定制依赖和政策窗口；
- 中期 3–5 年：市场扩张、标准化、复购、规模经济和竞争整合；
- 长期 5–10 年：结构性需求、技术替代、产业变化和可积累壁垒。

综合市场时机、快速变现、持续增长、可规模化、防御能力、替代风险、资源要求和资本适配，把每条路径归为窗口型快钱、现金流生意、长期复利型、高风险规模赌注或伪机会之一。类型不是固定分数映射，必须解释证据、假设和改变类型的条件。

## 证据边界

用户确认、系统假设、外部事实和推演结论分别标识。搜索量、讨论热度、点赞、媒体报道和宏观市场规模不能单独证明需求。公开投诉能证明问题存在，但不能自动证明购买意愿；没有访谈、订单、采购或持续付费证据时，不写“付费意愿已验证”。不为假想企业编造经营事实或精确预测。

L2/L3 中需求或竞争会影响路径取舍，按 `../core-evidence/references/decision-research-contracts.md` 建 `03_evidence/decision-research.json`，引用证据账而不复制证据。core-review 完成后、进入综合前运行 `python3 <运行时>/tools/research_quality.py check <任务文件夹>`；失败就补证据、缩窄主张或降级结论。

固定门禁顺序：core-review → research_quality check → core-synthesis。L1 不创建合同、不运行该检查。

## 审查与交付

L2、L3 先遵守 router 第 3.1 节的咨询交付合同；L1 不创建合同文件。

L2 起用 `../core-review/` 检查事实、反方和成品，特别检查是否漏掉替代方案、把热度当需求、把假设写成事实或只看短期窗口。之后用 `../core-synthesis/` 给每条路径下“值得推进 / 有条件推进 / 建议调整方向 / 暂不建议”之一，并给推荐路径的最小验证实验、成功、失败和停止标准。

最后用 `../core-storyline/` 组织内容，再按媒介交付：

- 默认正式报告：`out-report`，交付适合阅读的 A4 HTML + PDF。
- 路演或演示稿：`out-deck`，只在用户明确要路演、汇报、投屏、幻灯片或 deck 时使用。
- 用户明确指定媒介时以用户要求为准。同一任务可以同时交付两种媒介，二者不互相替代。

用运行时 `tools/package_support.py` 生成支撑包。主交付物和支撑包都经成品审查且 `08_deliverables/acceptance.json` 通过后，任务才完成。
